    BrandProfile Contract Specification¶

    Status: stable as of v0.79.0 (PR-30/31/32/33).

    This document describes the contract a new coffee-machine brand must satisfy to plug into the integration. The contract lives in custom_components/melitta_barista/brands/base.py as the BrandProfile Protocol and the MachineCapabilities dataclass.

    The integration's shared layers (ble_client.py, _ble_commands.py, _ble_recipes.py, HA entity platforms — sensor.py, button.py, select.py, number.py, switch.py) do not test brand_slug == "X" or import from brands.<vendor> directly. All brand-specific behaviour flows through the BrandProfile Protocol methods and per-family MachineCapabilities flags.

    1. Required BrandProfile surface¶

    Nivona HE brew starts are sent once. A missing or negative acknowledgment does not cause retransmission: the client instead polls HX for up to 15 seconds and accepts the start only if a fresh PRODUCT is observed on the original connection. READY, unknown processes and cached status do not confirm a start. The HA brew intent is staged before HE to cover status arriving before the ACK; an unconfirmed request is cleared. Required temporary recipe writes must all succeed before HE is sent.

    Identity¶

    brand_slug: str            # lowercase, no spaces; e.g. "melitta", "nivona"
brand_name: str            # display name; e.g. "Melitta", "Nivona"
service_uuid: str          # BLE GATT primary service UUID
ble_name_regex: re.Pattern[str]   # matches advertisement local_name
handshake_response_size: int      # bytes the handshake reply takes (8 for current brands)

    brand_slug is used in config-entry data and entity unique-ids; once released it MUST NOT change (it would orphan user devices).

    Capability tables¶

    supported_extensions: frozenset[str]    # BLE opcodes the brand exposes ("HC", "HJ", …)
families: dict[str, MachineCapabilities]  # family_key → caps

    supported_extensions documents which optional opcodes the brand firmware supports. Used by shared layers to decide whether to attempt e.g. read_recipe (HC). Current values:

    Brand supported_extensions
    Melitta {"HC", "HJ"}
    Nivona frozenset() (empty — uses HE-selector brewing)

    Crypto¶

    runtime_rc4_key: bytes              # 32-byte ASCII key
hu_table: bytes                     # 256-byte CRC table

def hu_verifier(self, buf: bytes, start: int, count: int) -> bytes:
    """2-byte handshake verifier — brand-specific table-driven fold."""

    The handshake verifier algorithm shape is the same across brands but the table values and the per-round offsets differ. Implement on the brand profile class.

    Family resolution + status parsing¶

    def detect_family(self, ble_name: str, dis: dict[str, str] | None) -> str | None:
    """Map advertisement local_name (+ optional DIS data) to a key in `families`."""

def capabilities_for(self, family_key: str) -> MachineCapabilities:
    """Return capability bag for the family. Raises KeyError if unknown."""

def parse_status(self, family_key: str | None, data: bytes,
                 *, status_profile_key: str | None = None):
    """Map an HX status payload to MachineStatus with brand-specific process codes."""

def can_confirm_prompt(self, status, caps) -> bool:
    """Whether the decoded status permits HY for this resolved model."""

    Different brands use different raw numbers for the same logical state. Examples observed in production: - Melitta: READY = 2, PRODUCT = 4 - Nivona NIVO 8000/9101: READY = 3, PRODUCT = 4 - Nivona 600/700/79x/900/1030/1040: READY = 8, PRODUCT = 11

    parse_status translates raw integers to the brand-agnostic MachineProcess enum.

    MachineCapabilities.status_profile_key optionally refines the incoming decoder for individual models sharing a capability family. The protocol passes it through both pushed and requested HX responses; profiles remain stateless. Nivona keeps raw process/subprocess/message codes and a diagnostic message_key separate from canonical enums. Any nonzero message blocks brewing, including errors and unknown messages that have no canonical manipulation token. This explicit blocker takes precedence over tolerated_brew_manipulations.

    Nivona permits HY only for recognized rinse confirmations in the resolved status profile, after receiving HX on the current connection. Physical actions such as filling water or replacing trays are visible but are not remotely acknowledgeable. Incomplete message profiles use conservative decoding: nonzero messages block brewing and cannot be confirmed. The experimental 9101 uses a separate Ef1109 decoder (ready3/home−1, product4) and does not inherit the 810x message/phase table. This does not enable any outgoing maintenance process codes. Melitta retains its canonical decoder and existing confirmation policy.

    Incoming mappings can be narrower than a capability family. The NICR 600 status profile recognizes the confirmed tray-missing (2) and fill-water (4) messages without assigning those codes to the incomplete 900 profile. The Ef698 profile recognizes PRODUCT sub-process 8 as water while retaining the machine's whole-drink progress. The NICR 795 refinement recognizes process 13 as a locally started frother rinse (EASY_CLEAN); this is passive observation and does not authorize a maintenance start command.

    MachineStatus.progress normalizes known scales to a percentage; raw_progress retains the received value. A decoder may set maintenance_raw_progress_max to require observed maintenance progression before a completion event. For the NICR 795 rinse, a clear READY must precede an incomplete rinse, progress must reach the raw maximum without interruption, and clear READY must follow. Missing or interrupted evidence produces no completion event.

    Shared commands check confirmation eligibility at invocation, inside the protocol lock on every attempt, and under the BLE write lock immediately before GATT transmission. A queued action belongs to one prompt appearance and connection; clearing/replacing the prompt invalidates it. Identical repeated HX frames and progress-only changes do not create a new appearance. Automatic confirmations remain opt-in and also recheck the option.

    Recipe write-path contract (v0.79.0+)¶

    These methods exist so shared mixins (_ble_commands, _ble_recipes) and HA platforms don't import from brands.<vendor> directly. Brands that don't expose the corresponding feature return None / 1 / False stubs.

    temp_recipe_type_register: int | None      # ClassVar — fixed HW register or None

def temp_recipe_register(self, family_key, recipe_id, field) -> int | None: ...
def fluid_write_scale(self, family_key) -> int: ...      # 1 by default, 10 for some families
def mycoffee_layout(self, family_key) -> RecipeFieldLayout | None: ...
def mycoffee_register(self, slot, offset) -> int | None: ...
def is_chilled_selector(self, selector) -> bool: ...
def validate_recipe_param(self, caps, context, selector, field, value) -> int: ...
    Method Returns when not supported
    temp_recipe_type_register None (class attribute)
    temp_recipe_register None
    fluid_write_scale 1
    mycoffee_layout None
    mycoffee_register None
    is_chilled_selector False

    validate_recipe_param normalizes integral input and raises ValueError for unsupported fields or invalid known domains. Context is temporary, standard or mycoffee; a domain must not be copied between these contexts. Shared commands preflight the whole explicit override set before the first HW. Persistent numeric services translate validation errors into HA service validation errors. Choice values retain their raw numeric meaning.

    Persistent storage resolution is family-aware. Call standard_recipe_register(selector, offset, family_key=caps.family_key) for both validation and transmission; a nullable result means the mapping is unsupported. The two-argument arithmetic helper is retained for compatibility and must not be used to choose actual write addresses. Storage bases do not renumber the released HE drink catalog. Conflicting pure-milk mappings and unknown standard selectors are rejected before any HW write.

    For Nivona 960/965/970 (integration family 900-light), both standard and MyCoffee layouts declare fluid_write_scale_10=True: all quantity writes use mL ×10; other recipe choices are unscaled. The 900 family (920/930) retains its existing identity conversion. MyCoffee cache entries remain raw; amount sensors convert at presentation time and expose raw_value separately. recipe_amount_unit permits a verified display unit without guessing from brand/family names in shared entities.

    Nivona numeric domains use separate context tables. Standard quantity/choice limits bind an absolute register address and semantic field; unresolved or conflicting mappings retain the integer wire domain rather than inheriting another recipe's limits. Zero remote quantities remain valid disable/default sentinels alongside model-specific nonzero ranges. Native strength levels 1–N map to raw0–N−1 only at the native button boundary; the numeric API is already raw and is not shifted. Native inputs use live model capabilities, revalidate restored values and retain unsupported entity IDs as unavailable.

    2. Required MachineCapabilities fields¶

    Each entry in families is a MachineCapabilities dataclass with these mandatory fields:

    family_key: str            # matches dict key — used by parse_status etc.
model_name: str            # surfaced as HA `model` attribute on the device

    Feature flags (defaults shown)¶

    supports_recipe_writes: bool = False    # HC/HD/HJ recipe editing
supports_stats: bool = False            # has populated `stats` tuple
supports_factory_reset: bool = False    # firmware exposes factory-reset HE commands
supports_brew_overrides: bool = False   # per-brew temp-recipe slot pattern
uses_legacy_total_cups_sensor: bool = False  # Melitta-only hand-tailored sensor

my_coffee_slots: int = 0
strength_levels: int = 5
has_aroma_balance: bool = False
first_mycoffee_selector: int = 20       # family-specific MyCoffee HE base: 8, 10 or 20

    Protocol quirks¶

    fluid_scale_factor: int = 1             # raw quantity units per mL
brew_water_amount_max: int = 240        # native mL control, refined per model
recipe_amount_unit: str | None = None   # verified display unit
brew_command_mode: int = 0x0B           # HE byte; 0x04 for NIVO 8000
recipe_text_encoding: str = "legacy_1byte"   # vs "utf16_le"
status_profile_key: str | None = None       # model-refined incoming HX profile
tolerated_brew_manipulations: tuple[int, ...] = ()  # Manipulation flags that don't block brew
saved_recipe_only_selectors: tuple[int, ...] = ()
saved_recipe_only_firmwares: tuple[str, ...] = ()
required_brew_overrides: tuple[tuple[int, str, int], ...] = ()
brew_temperature_max: tuple[tuple[int, int], ...] = ()
brew_profile_options: tuple[tuple[int, str], ...] = ()  # raw value / native option
brew_profile_recipe_ids: tuple[int, ...] = ()          # eligible coffee selectors

    The saved-recipe workaround applies only when both the selector and exact firmware match; explicit temporary overrides are rejected before any write. required_brew_overrides contains (selector, field, raw_value) triples that must be applied after user overrides when starting a temporary recipe. This keeps fixed preparation presets from being overwritten by generic controls. brew_temperature_max narrows the existing raw0–2 input domain per selector. The brand's temp_recipe_register resolves the legacy temperature alias to the recipe's actual process field, returning None when unsupported. Shared commands consume this metadata without inferring behavior from family names. brew_profile_options and brew_profile_recipe_ids expose a separate native flow-profile override only for confirmed models. Empty tuples disable it; this does not change the legacy has_aroma_balance meaning.

    Tables (filled per family)¶

    recipes: tuple[RecipeDescriptor, ...] = ()      # drink selectors
settings: tuple[SettingDescriptor, ...] = ()    # HR-readable settings
stats: tuple[StatDescriptor, ...] = ()          # HR counters

    Each StatDescriptor declares the register ID, display/translation key, title, unit and diagnostic category. Optional value_mask selects the count bits of a packed register; shared sensors must not guess a width from the brand or family. Optional entity_key preserves an already released HA unique ID when the display key is corrected. It identifies the same physical register and must be unique within the family's stats table. unit="count" denotes an increasing counter; unit=None can represent a warning flag or a raw usage gauge with unknown units and no statistics state class.

    Capability-driven statistics use one entry-local read queue. Reads run on connection, after a busy-to-ready transition and every five minutes while idle. Concurrent requests share a pass, failed reads keep cached values, and successful zeros or decreases remain valid. Disconnect/unload cancels active reads. None of these refreshes changes the persisted recipe or machine settings.

    The client reads these registers through read_statistic(stat_id), authorized by membership in the currently resolved caps.stats. It returns the raw HR value; presentation applies descriptor masks. read_setting retains its independent settings allowlist. Statistics descriptors do not grant setting read or write access, and a stale descriptor cannot authorize a register on a newly resolved model.

    Native capability-driven settings and brew inputs must also be registered when capabilities become available after an offline platform setup. Reconnects must not duplicate unique IDs, subscriptions must be removed on entry unload, and newly added setting entities must read values if already connected.

    Important: Melitta leaves settings = () even though it has settings entities — Melitta's settings are surfaced through the legacy hand-coded MachineSettingSelect/Number/Switch entities (driven by const.MachineSettingId), not the capability-driven BrandSettingX entities. The capability-driven entities check if caps.settings: and skip when empty.

    3. How to add a new brand¶

    Step 1 — create the package¶

    brands/<vendor>/
  __init__.py              # YourProfile class + module-level helpers
  _crypto.py               # RC4 key + HU table constants (if brand-wide)
  _options.py              # setting-option enums (optional)
  _registers.py            # register bases + address helpers (if brand has them)
  _stats_helpers.py        # _count / _pct / _flag factories (optional)
  _prefixes.py             # serial-prefix → family map (if multiple families)
  _family_<key>.py         # one per family, exporting CAPABILITIES + EXPORTS dict

    Patterns for _family_*.py and the EXPORTS aggregation loop in __init__.py are documented in brands/nivona/ — copy that structure.

    Step 2 — implement the BrandProfile Protocol¶

    Minimum boilerplate:

    class YourProfile:
    brand_slug: ClassVar[str] = "your_vendor"
    brand_name: ClassVar[str] = "Your Vendor"
    service_uuid: ClassVar[str] = "..."
    handshake_response_size: ClassVar[int] = 8
    ble_name_regex: ClassVar[re.Pattern[str]] = re.compile(r"^...")
    supported_extensions: ClassVar[frozenset[str]] = frozenset()
    families: ClassVar[dict[str, MachineCapabilities]] = _YOUR_FAMILIES

    # Crypto + handshake — required
    @property
    def runtime_rc4_key(self) -> bytes: ...
    @property
    def hu_table(self) -> bytes: ...
    def hu_verifier(self, buf, start, count) -> bytes: ...

    # Family resolution + status parsing — required
    def detect_family(self, ble_name, dis=None) -> str | None: ...
    def capabilities_for(self, family_key) -> MachineCapabilities: ...
    def parse_status(self, family_key, data, *, status_profile_key=None): ...
    def can_confirm_prompt(self, status, caps): ...

    # Recipe write-path — implement or use stub returns
    temp_recipe_type_register: ClassVar[int | None] = None
    def temp_recipe_register(self, *a) -> int | None: return None
    def fluid_write_scale(self, family_key) -> int: return 1
    def validate_recipe_param(self, caps, context, selector, field, value) -> int: ...
    def mycoffee_layout(self, family_key) -> RecipeFieldLayout | None: return None
    def mycoffee_register(self, slot, offset) -> int | None: return None
    def is_chilled_selector(self, selector) -> bool: return False

    Step 3 — register in brands/__init__.py¶

    from .your_vendor import YourProfile
# add YourProfile() to the BrandRegistry instance

    Step 4 — add tests¶

    Minimum test coverage: - test_brands.py::test_<vendor>_* — verify family detection, HU verifier with a known vector, capability shape - test_protocol.py::test_<vendor>_handshake_* — verify handshake reply matches expected verifier output - test_<vendor>_parse_status — pin process-code dispatch

    4. Anti-patterns¶

    These were removed in v0.79.0 and MUST NOT come back:

    ❌ if client.brand.brand_slug == "your_vendor": ... in shared layers → use a capability flag on MachineCapabilities.

    ❌ from .brands.your_vendor import some_helper in shared layers → lift the helper to a BrandProfile method with a stub on other brands.

    ❌ isinstance(client.brand, YourProfile) → same — use capability flag.

    ❌ Hardcoded family-key lists like _FACTORY_RESET_FAMILIES = {"600", ...} → use capability flag on MachineCapabilities.

    ❌ Mutating MachineCapabilities fields after construction → it's @dataclass(frozen=True); use dataclasses.replace().

    5. What's NOT in the contract yet¶

    Forward-looking — not blocking new brands today, but worth flagging:

    • No external plugin loader. All brands live in-tree. Adding a 4th brand still requires editing brands/__init__.py to register the profile. Plugin-from-disk discovery is deliberately not built.
    • No versioning of the Protocol surface. Adding a method to BrandProfile is a breaking change for any out-of-tree implementer. There are zero out-of-tree implementers today, so we move freely.
    • No formal capability-coverage test framework. A new brand passing 0 tests is technically allowed; we rely on PR review to catch missing coverage.

    When/if these become bottlenecks (community-driven 3rd brand, external plugin requests), revisit. Until then the contract above is sufficient.

    NIVO 9101 recipe preparation¶

    9101 has an independent family: standard selectors0..12, explicit storage bases (Lungo10100, Espresso10000), MyCoffee selectors13..28 and16 slots. Quantities are in mL. Unresolved or unsupported recipe fields fail before transmission. Its remote Type register is9000, strength9001, and remote HE uses selector0. The remote template is filled completely from verified defaults and current saved fields before explicit overrides; missing reads or rejected writes abort the start. This prevents parameters from an earlier temporary recipe leaking into a later one. Chilled recipes require profile5, without an8107 temperature99 requirement or firmware fallback.

    Recipe starts and numeric recipe/setting writes use the capability's optional recipe_write_precondition under one shared operation lock: a current ready/home status, then one HE98 ACK, then dependent writes/start. A negative ACK or timeout aborts; no inferred home polling or preparation retry is added. Maintenance commands remain unavailable. AutoOn schedules and recipe reordering are withheld until their conflicting domains are resolved.

    Model settings use verified/writable descriptors. Unsupported controls are disabled in the entity registry without removing custom names. The legacy AutoOn key/ID remains stable while its label describes automatic switch-on.
